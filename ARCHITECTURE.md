# Zync — Architecture

Technical overview of how Zync is structured, how the pieces talk to each other, and where to find things. For features and setup, see the [README](README.md).

## Overview

Zync is an npm-workspace-style **monorepo** with two independently deployed apps and Firebase as the shared backend-as-a-service.

```
┌──────────────┐   Firebase ID token (Bearer)   ┌──────────────┐
│   client/    │ ─────────────────────────────► │   server/    │
│  React SPA   │                                │  Express API │
│  (Vercel)    │ ◄───────────── JSON ────────── │  (Render)    │
└──────┬───────┘                                └──────┬───────┘
       │ Firebase JS SDK (auth)                        │ firebase-admin
       ▼                                               ▼
┌─────────────────────────────────────────────────────────────┐
│            Firebase Auth  +  Cloud Firestore                 │
└─────────────────────────────────────────────────────────────┘
```

## Tech Stack

- **Frontend**: React 19, TypeScript, Vite (SWC), React Router v7, Vanilla CSS, PWA (`vite-plugin-pwa` + Workbox)
- **Backend**: Node.js, Express 5, TypeScript
- **Database & Auth**: Firebase Authentication + Cloud Firestore (`firebase-admin` on the server, Firebase JS SDK on the client)
- **HTTP**: Axios (client) ↔ REST JSON API (server)
- **Drag & Drop**: `@hello-pangea/dnd`
- **Icons**: `lucide-react`

## Frontend

- **SPA + lazy routing**: [router/index.tsx](client/src/router/index.tsx) defines a `createBrowserRouter` tree. All feature pages are `React.lazy` + `Suspense` for code-splitting. Routes sit behind a `ProtectedRoute`; auth pages (`/login`, `/signup`) are outside it.
- **Auth state**: [AuthContext.tsx](client/src/context/AuthContext.tsx) wraps the Firebase JS SDK — email/password, Google (`GoogleAuthProvider`), and Apple (`OAuthProvider`) sign-in. The current user is cached in `localStorage` (`zync_auth_user`) for instant rehydration on reload.
- **API client**: [services/api.ts](client/src/services/api.ts) is a shared Axios instance. A request interceptor awaits Firebase's `onAuthStateChanged` (`authReady`) before each call to avoid first-load 401s, then attaches the current user's Firebase **ID token** as `Authorization: Bearer <token>`. Base URL is `VITE_API_URL/api`, falling back to `/api` (Vite dev proxy → `127.0.0.1:3000`).
- **Service layer**: one wrapper per domain (`boardService`, `taskService`, `goalService`, `checkInService`, `dashboardService`, `quoteService`) keeps components free of HTTP detail.
- **PWA**: [vite.config.ts](client/vite.config.ts) registers `vite-plugin-pwa` with `registerType: "prompt"` — the service worker pre-caches the app shell (Workbox) and the [UpdatePrompt](client/src/components/UpdatePrompt.tsx) component asks the user before applying a new version. Manifest lives in [client/public/manifest.json](client/public/manifest.json); icons are generated by [scripts/generate-icons.mjs](client/scripts/generate-icons.mjs).

## Backend

- **Express 5 REST API**: [server/src/index.ts](server/src/index.ts) configures CORS (credentialed, origin from `FRONTEND_URL`), JSON + cookie parsing, a request-timing logger, and mounts routers under `/api/*`. A public `GET /api/health` reports liveness.
- **Auth middleware**: [middleware/auth.ts](server/src/middleware/auth.ts) extracts the `Bearer` token, verifies it with `firebase-admin` `auth.verifyIdToken()`, and attaches `req.user.userId` (the Firebase UID). Every domain router calls `router.use(authenticateToken)` — all data routes are protected.
- **Firestore access**: [lib/firebase.ts](server/src/lib/firebase.ts) initializes `firebase-admin` (credential from `FIREBASE_SERVICE_ACCOUNT` JSON or `GOOGLE_APPLICATION_CREDENTIALS`, fails fast if missing) and exports `db`, `auth`, plus `Timestamp`↔`Date` helpers. Controllers scope every query by `userId` for per-user data isolation.
- **Note**: a `server/prisma/schema.prisma` file exists but is **not used** — the API runs entirely on Firestore. Do not run `prisma generate` during deploy.

## Auth flow

1. User signs in on the client via the Firebase JS SDK (email/password or OAuth).
2. Firebase issues an **ID token**; the Axios interceptor attaches it as a Bearer header on every API request.
3. The Express `authenticateToken` middleware verifies the token with `firebase-admin` and resolves the Firebase UID.
4. Controllers read/write Firestore documents filtered by that `userId`.

## Data model (Firestore collections)

| Collection      | Holds                                                          |
| --------------- | ------------------------------------------------------------- |
| `boards`        | Kanban boards and their columns                               |
| `tasks`         | Tasks & subtasks (`parentId`), linked to goals via `goalId`   |
| `goals`         | Goals with progress, target date, category, milestones        |
| `dailyCheckIns` | Journaling entries: work log, mood, focused hours, reflections |

Document shapes are mirrored in the client's [types/index.ts](client/src/types/index.ts) (`Task`, `KanbanTask`, `Goal`, etc.). Firestore composite indexes are declared in [server/firestore.indexes.json](server/firestore.indexes.json).

## API endpoints

All routes are under `/api` and require a valid Firebase ID token (except `/api/health`).

| Method   | Path                     | Purpose                          |
| -------- | ------------------------ | -------------------------------- |
| `GET`    | `/api/health`            | Liveness check (public)          |
| `GET`    | `/api/auth/me`           | Current authenticated user       |
| `GET`    | `/api/boards`            | List boards                      |
| `POST`   | `/api/boards`            | Create board                     |
| `GET`    | `/api/boards/:id`        | Get board                        |
| `POST`   | `/api/boards/columns`    | Create column                    |
| `POST`   | `/api/tasks`             | Create task                      |
| `GET`    | `/api/tasks/:id`         | Get task                         |
| `PUT`    | `/api/tasks/:id`         | Update task                      |
| `PATCH`  | `/api/tasks/:id/complete`| Mark task complete               |
| `DELETE` | `/api/tasks/:id`         | Delete task                      |
| `GET`    | `/api/goals`             | List goals                       |
| `POST`   | `/api/goals`             | Create goal                      |
| `GET`    | `/api/goals/:id`         | Get goal (with linked tasks)     |
| `PUT`    | `/api/goals/:id`         | Update goal                      |
| `DELETE` | `/api/goals/:id`         | Delete goal                      |
| `GET`    | `/api/checkins`          | List check-ins                   |
| `POST`   | `/api/checkins`          | Create check-in                  |
| `GET`    | `/api/checkins/:id`      | Get check-in                     |
| `PUT`    | `/api/checkins/:id`      | Update check-in                  |
| `DELETE` | `/api/checkins/:id`      | Delete check-in                  |
| `GET`    | `/api/dashboard`         | Aggregated dashboard data        |
